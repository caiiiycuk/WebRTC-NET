# Design

## Context

Мотивация приведена в `proposal.md`. Исследованы текущие `coturn-docker` и submodule `3rdparty/coturn` на commit `d08cf551685f45dc6603dbaf5854f4fa54fdd67f`.

- В `src/apps/uclient/uclient.c` ветка TLS функции `recv_buffer` передаёт весь результат `SSL_read` одним `stun_buffer`. `process_received_buffer` ожидает одно сообщение. Ветка plain TCP уже определяет длину через `stun_get_message_len_str`; для `atc` она отдельно обрабатывает raw TCP relay payload.
- Диагностика 11.11.2026 показала чтения TLS по 104 и 208 байтов: все шесть frames пришли, но тестер посчитал четыре сообщения. `-z 1000` обходил ошибку, не доказывая исправление framing. Отдельный тестер Ubuntu coturn 4.6.1 получал `Bad channel number`; это другая проблема совместимости, не повод менять серверный bind.
- `coturn-docker/Dockerfile` использует `ghcr.io/caiiiycuk/coturn:4.18.0-3`. Образ выпускается только release tag форка через `.github/workflows/release-image.yml`; существующий основной spec требует совпадения pin и submodule commit.
- Coturn работает в `network_mode: host`. Шаблон задаёт `prometheus-address=127.0.0.1`; publisher обращается к `http://127.0.0.1:9641/metrics`. Поэтому для внешнего IPv4 scrape достаточно другого bind без Docker port mapping и без изменения publisher.
- В README и подсказке `init.sh` есть `rm .env && docker compose down -v`; раздел backup не включает `coturn-data`. Активный соседний change о deadline capacity изменяет другие части README и publisher; его логику и артефакты не затрагиваем.

## Goals / Non-Goals

**Goals:** исправить приём control frames в настоящем TLS пути тестера, обеспечить воспроизводимые тесты границ чтения и поставить этот тестер через закреплённый образ. Открыть default listener метрик с явным описанием новой границы доступа. Сделать инструкции проверки и обслуживания безопасными для существующего volume.

**Non-Goals:** менять TURN server data path, UDP/DTLS алгоритмы, raw TCP relay protocol, cloud, quotas, capacity history или формат публикаций. Не добавлять exporter, авторизацию HTTP, TLS proxy метрик, новый orchestrator или обязательные зависимости. Не изменять firewall/DNS/VPS и не публиковать wiki в рамках этого change.

## Decisions

### 1. Восстанавливать control frames, а не замедлять тест

Использовать существующие wire-format проверки coturn, включая `stun_get_message_len_str`, для определения полной длины STUN/ChannelData и stream padding. Сохранять ограниченное состояние незавершённого чтения на конкретном TLS-соединении. Отдавать обработчику один полный frame, сохраняя остальное; следующие полные frames должны обрабатываться даже без нового сетевого события. Частичные заголовок и payload не теряются при `WANT_READ`/`WANT_WRITE`; ожидание готовности не заменяется busy loop. Завершение соединения и invalid/oversize length дают ошибку, а не успешную доставку обрезанных данных.

Не распространять STUN framing на raw data connection TCP relay. Его отличает существующий контекст `data_connection`/`atc`; начало payload может выглядеть как заголовок STUN. Состояние приёма размещать в существующей структуре соединения в `session.h`, только если это нужно для сохранения между вызовами, и освобождать вместе с соединением. Не создавать глобальный буфер или новый универсальный транспортный слой.

Альтернативы: увеличение `-z` скрывает ошибку, а предположение «одна TLS record = один frame» не соответствует stream semantics. Слепое применение plain `MSG_PEEK` к сокету TLS читает шифротекст, поэтому его нельзя копировать буквально.

### 2. Регрессия должна воспроизводить формы потока детерминированно

Добавить небольшой C-test target в существующий `3rdparty/coturn/tests/CMakeLists.txt` с `BUILD_TESTING=ON`. Проверять именно код, используемый TLS receiver, подавая контролируемые chunks: несколько frames одним чтением, заголовок по частям, payload по частям, полный frame с хвостом следующего, STUN + ChannelData + padding + Data indication, закрытие и неверную длину. Проверить временное отсутствие данных, независимость двух соединений и raw data режим. Отдельно нужен интеграционный TLS relay smoke реальным тестером и совместимым coturn при штатном интервале отправки; только тест изолированного wire parser не доказывает исправление receiver.

UDP и plain TCP остаются контрольными сценариями; существующие DTLS/TCP relay проверки не отключаются. Положительный итог требует равных ненулевых data counters и нулевых потерь. Формат отчёта не исправляется искусственной коррекцией счётчиков.

### 3. Минимально изменить default метрик

Заменить единственную строку шаблона на `prometheus-address=0.0.0.0`. Порт остаётся `9641`; адрес publisher, scrape deadline/body limit, peer deny list и Compose networking не меняются. Новый env-параметр не нужен: для локального режима оператор явно возвращает `127.0.0.1` в template.

README должен согласованно описывать внешний bind во всех разделах, показывать локальный и удалённый scrape, пример firewall allowlist для адреса/CIDR мониторинга и предупреждать, что endpoint не шифруется и не аутентифицирует читателя. Это не команда открыть порт всему интернету и не автоматическая правка firewall. В изолированном Linux network namespace проверить доступ по не-loopback адресу и loopback scrape; затем вернуть bind на loopback и проверить отказ внешнего подключения. Проверять реальные HTTP response и существующие traffic/quota/snapshot families.

### 4. README является эксплуатационной инструкцией, а не протоколом испытаний VPS

Обновить `Testing TURN` двумя bounded relay-тестами с отдельной машины: UDP и TLS с paired clients, payload и строгими counters. Использовать тестер из точно указанного совместимого образа, не случайный пакет дистрибутива. Показать получение временных credentials без `echo` значений и без `set -x`; shared secret не копировать на недоверенный узел. Если credentials передаются аргументами тестера, явно описать их видимость локальным процессам и использовать доверенную машину. Для прежнего образа отдельно описать временный `-z 1000`, не выдавая его за проверку исправленного тестера или capacity calibration.

Backup описать для фактического Compose project, а не только hardcoded `coturn-docker_*`: остановить writer, сохранить private `.env`, cert volume и весь `coturn-data`, восстановить в те же volumes до старта. Проверять сохранение watermark, identity и traffic fixture. Не объединять вручную JSON и не инициализировать историю вместо утраченной.

Для staging → production сохранить `.env` и volumes, получать production-сертификат явно через production ACME server с тем же domain/lineage, учитывая занятый standalone port, и перезапускать только потребителей сертификата. Точные команды проверить fixture с fake Docker/certbot: без `down -v`, удаления `.env` и реального запроса сертификата. Подсказка `init.sh` должна указывать этот же недеструктивный сценарий; менять весь интерактивный installer не требуется. Исправить упоминание обязательного `443` для TURNS на используемый порт `5349` и сохранить отдельное назначение HTTPS ping `8000`.

### 5. Выпускать исправление через существующую release цепочку

Изменения тестера принадлежат git-истории форка, не патчу поверх опубликованного образа. После тестов подготовить новый `release/<coturn-ver>-<N>`, собранный штатным workflow, затем обновить `FROM` и gitlink `3rdparty/coturn` до того же release commit. Не использовать `latest`, не менять прежний tag/asset и не указывать несуществующий образ. Новый архив dzcoturn, если выпускается при согласованной поставке, получает следующий свободный номер и согласованные README/template.

Публикация требует отдельного разрешения; без него release/pin-проверка остаётся открытой, а недостающий образ не объявляется выпущенным. Синхронизация публичной GitHub wiki остаётся отдельной работой. Старый cloud pacing workaround здесь не удаляется: его изменение в другом проекте не требуется для этого контракта.

## Risks / Trade-offs

- Публичные метрики могут раскрывать эксплуатационные данные → breaking change заметно описывается, firewall ограничивается адресами мониторинга; loopback opt-out проверяется.
- TLS может вернуть уже расшифрованные данные без нового события сокета → тесты проверяют несколько buffered frames и отсутствие зависания между ними.
- Обновление тестера затрагивает error handling и synchronous/nonblocking вызовы → проверяются оба пути, partial EOF, invalid lengths и cleanup; raw TCP relay отделён.
- Pacing может случайно скрыть регрессию → исправленный receiver и новый образ проверяются при обычном интервале, обход описан только для старой версии.
- Одновременные изменения README в capacity change → правки ограничиваются разделами проверки, backup, staging и metrics; не менять правила истории или закрывать чужие задачи. Исключение: фраза раздела `Capacity publication and recovery` о bind метрик на `127.0.0.1` и заметка в разделе security противоречили бы новому default; в разделе capacity менять только эту фразу, чтобы не конфликтовать с задачей 1.6 change `harden-capacity-history-against-deadline`.
- Сертификатная инструкция может удалить прежнюю identity или вызвать ACME rate limit → fixture проверяет сохранность `.env`/volumes, production ACME не вызывается автоматически.

## Migration Plan

1. Реализовать и проверить receiver в форке; прогнать C-tests, sanitizers на новых тестах, UDP/TCP/TLS smoke и регрессии обёртки.
2. Выполнить все сборки Linux-целей HumbleNet и отдельно `ninja -j32 webrtcnet` из `emscripten`. Проверить `bash -n`, Python tests и OpenSpec.
3. После отдельного разрешения опубликовать новый tag/image и проверить его происхождение; обновить согласованные pin/gitlink и проверить тестер внутри нового образа. Проверить содержимое нового архива, если публикация архива разрешена.
4. Документировать opt-out метрик до обновления работающей установки. Деплой выполняется отдельно оператором с прежним Compose project, `.env` и volume; в этом change работающий VPS не трогается.
5. Возврат к прежнему image и loopback template не требует удаления volumes или сброса истории; при rollback тестера возвращается прежнее ограничение TLS framing, а не гарантия исправления.
