## ADDED Requirements

### Requirement: Внешний Prometheus по умолчанию

Поставляемый шаблон dzcoturn SHALL включать Prometheus на IPv4 `0.0.0.0:9641`, сохраняя доступ `http://127.0.0.1:9641/metrics` для publisher и существующие семейства метрик. Инструкция MUST явно сообщать, что HTTP endpoint не имеет авторизации и TLS, и описывать разрешение TCP `9641` только адресам мониторинга в host/provider firewall. Она SHALL описывать явный возврат `prometheus-address=127.0.0.1` для локального мониторинга. Изменение default MUST NOT автоматически менять firewall работающего сервера.

#### Scenario: Scrape с другого хоста
- **WHEN** контейнер запущен с default template и network mode host, а firewall разрешает источник мониторинга
- **THEN** другой хост получает Prometheus response через IPv4 адрес TURN-сервера и TCP `9641`
- **AND** локальный publisher продолжает получать те же метрики через loopback

#### Scenario: Явно выбран локальный режим
- **WHEN** оператор устанавливает `prometheus-address=127.0.0.1` в шаблоне и применяет его
- **THEN** локальный scrape работает, а внешний адрес не предоставляет endpoint

### Requirement: Достоверная инструкция проверки relay

README SHALL содержать внешнюю UDP и TLS relay-проверку тестером из совместимого закреплённого образа. Успех MUST требовать фактической передачи payload, положительных равных счётчиков отправки/получения и нулевых потерь; одного STUN binding, TURN allocation или TLS handshake недостаточно. Примеры MUST NOT выводить shared secret или временные credentials в логи и MUST предупреждать о возможной видимости аргументов процесса на машине тестера.

#### Scenario: Внешняя проверка исправленным тестером
- **WHEN** оператор выполняет документированные UDP/TLS проверки с отдельной машины и временными credentials
- **THEN** инструкции позволяют отличить успешную передачу от одной лишь доступности порта
- **AND** TLS проверяется при обычном интервале отправки, без обязательного увеличения паузы

#### Scenario: Прежний тестер
- **WHEN** используется старый несовместимый тестер или образ с известной ошибкой TLS framing
- **THEN** инструкция различает `Bad channel number` и ошибочный подсчёт объединённых TLS frames
- **AND** pacing обозначен только временным обходом, не исправлением сервера и не измерением capacity

### Requirement: Состояние сохраняется при обслуживании

README и сообщения перехода staging → production SHALL сохранять `.env`, identity, существующий `coturn-data` и сертификаты. Backup MUST включать весь `coturn-data`, включая `capacity_state.json` и traffic state, сниматься согласованно с остановленным писателем и восстанавливаться до запуска publisher. Инструкции MUST NOT предлагать `down -v`, удаление `.env` или повторную инициализацию истории как штатное обновление сертификата. Потеря истории прежнего сервера MUST NOT трактоваться как новая identity.

#### Scenario: Staging сменяется production
- **WHEN** оператор следует README или подсказке `init.sh` для смены issuer сертификата
- **THEN** сохраняются прежние секрет, domain, публикационный барьер и traffic state, а production-сертификат получается без удаления постоянных volumes

#### Scenario: Восстановление данных
- **WHEN** оператор восстанавливает резервную копию прежнего сервера
- **THEN** сначала восстанавливаются конфигурация и согласованный volume в фактически используемый Compose project
- **AND** после запуска история не сбрасывается и старый watermark не объявляется новой историей

#### Scenario: История прежнего сервера отсутствует
- **WHEN** `capacity_state.json` утрачен или невалиден
- **THEN** инструкция сохраняет существующее поведение без автоматического создания новой истории; ICE/traffic и capacity описываются отдельно

### Requirement: Исправленный тестер поставляется воспроизводимо

Новая поставка dzcoturn SHALL использовать новый явно закреплённый release image с исправленным TLS framing. Commit `3rdparty/coturn` MUST совпадать с commit release tag этого образа, как требует существующая политика проекта. Прежние опубликованные image tags и release assets MUST NOT перезаписываться; номер следующей поставки выбирается по доступным версиям при выпуске.

#### Scenario: Проверка новой поставки
- **WHEN** выпускается согласованная новая версия
- **THEN** тестер внутри образа проходит regression framing и UDP/TLS relay smoke при обычном интервале
- **AND** pin, release tag и commit submodule однозначно соответствуют друг другу
