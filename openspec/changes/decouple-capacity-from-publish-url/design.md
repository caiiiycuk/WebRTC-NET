# Design

## Context

Мотивация описана в `proposal.md`. В `coturn-docker/publisher.py` адрес входит в `self.binding`; конструктор сравнивает с ним весь сохранённый binding. Перед каждой попыткой capacity файл сравнивается с ожидаемым состоянием целиком. Замены только начального сравнения недостаточно: следующая проверка снова отключит `known`.

`attemptedThroughMs` записывается атомарно с fsync до отправки `known`. После перезапуска положительный watermark сначала означает `unknown`; здоровый строго более новый снимок разрешает `known`. Process lock не допускает несколько publisher на одном volume. Эти механизмы сохраняются.

Существующий основной spec не определяет идентичность истории capacity. Delta добавляет отдельные требования к существующей capability `coturn-docker-image`; не заменяет её требование `Container behavior is preserved` и не пересекается с управлением процессами в `restart-coturn-publisher`.

## Goals / Non-Goals

**Goals:**
- Разделить адрес доставки и идентичность истории без изменения формата файла.
- Сохранить строгий контроль изменений состояния во время работы.
- Прочитать существующий файл с устаревшим URL без записи при загрузке и без сброса барьера.

**Non-Goals:**
- Не добавлять alias-списки, нормализацию URL, переменные окружения или миграционную команду.
- Не поддерживать горячую перезагрузку окружения и одновременную отправку на несколько URL.
- Не переносить историю между разными `DOMAIN` или независимыми publisher-volume.
- Не менять источник метрик, payload, таймауты, process lock, entrypoint и Cloud.

## Decisions

### Проверять идентичность по домену, сохранять исходный binding

При загрузке проверять корректность структуры версии 1, домен и допустимый целочисленный watermark. Сохранённый binding должен иметь прежнюю структуру с доменом и строковым `publishUrl`, но его URL не сравнивается с текущим окружением. После успешной проверки принять сохранённый binding как ожидаемый binding файла для этого процесса.

Текущий `PUBLISH_URL` по-прежнему берётся из окружения для HTTP-запросов и проверяется при запуске. Сохранённый URL является только метаданными истории; его доступность, совпадение с текущим адресом и соответствие текущим сетевым требованиям не определяют пригодность истории.

Альтернатива с удалением поля меняет формат и требует миграции. Автоматическая перезапись поля при старте добавляет запись и обработку её отказа без необходимости. Сохранение прежнего binding решает задачу меньшим изменением.

### Не ослаблять повторную проверку файла

Существующее сравнение полного сохранённого состояния с ожидаемым сохранить, но использовать принятый с диска binding, а не сконструированный из текущего URL. Новые записи watermark сохраняют этот же binding. Это устраняет повторное отключение из-за различия адресов и продолжает обнаруживать любое внешнее изменение принятого состояния, включая изменение его URL.

Инициализация действительно новой истории остаётся прежней: версия 1, текущий домен и URL, watermark 0. Чтение и повторная запись такого файла после смены URL не обнуляют watermark. Отдельные функции-обёртки и универсальная система миграций не нужны.

### Не менять восстановление после перезапуска

Существующий положительный барьер остаётся положительным даже при смене адреса. Равный снимок после перезапуска не восстанавливает потерянный frozen tuple и остаётся `unknown`; строго больший здоровый watermark сохраняется до отправки `known`. Потеря файла не превращается в новую идентичность.

### Проверить реальную отправку и сохранение состояния

В `test_publisher.py` использовать существующие fixtures метрик, временный каталог и локальный HTTP fixture. Проверить различающиеся URL, несколько последовательных снимков и повторный запуск, отправку на текущий адрес, сохранение исторического binding и рост watermark. Равный положительный watermark должен дать `unknown`, а следующий здоровый снимок должен дать `known`.

Отдельно проверить другой домен, неверные типы binding/watermark, повреждение или удаление файла, его внешнее изменение, отказ durable write и прежние проверки источника/HTTPS. Тестовый HTTP endpoint остаётся внутренним fixture; production-проверка HTTPS не ослабляется.

## Risks / Trade-offs

- Сохранённый URL может отличаться от реального назначения и путать оператора → README явно описывает поле как исторические метаданные; фактический адрес определяется окружением.
- URL может вести на другой backend с независимой историей → перенос его истории не обещается; локальный монотонный барьер сохраняется и не обнуляется ради доставки.
- Старая версия publisher после отката снова потребует совпадения URL → заранее указать ограничение; не удалять state и не восстанавливать устаревшую резервную копию поверх новых попыток ради отката.
- Рабочее дерево уже содержит изменения publisher, тестов и документации → накладывать только этот небольшой diff, не перезаписывать чужую работу и не включать её автоматически в change.

## Migration Plan

Предварительная миграция состояния не нужна. При отдельном разрешении на deploy обновить publisher с сохранением volume и перезапустить его штатным способом. Проверить положительный watermark, успешные публикации и появление свежей capacity в Cloud. Этот change не разрешает production-deploy.

При откате сохранить актуальный файл со всеми попытками. Если сохранённый URL отличается от текущего, старая версия отключит capacity; не обходить это сбросом истории. Для безопасного отката использовать исправленную версию либо отдельно согласованное согласование binding после остановки publisher с сохранением актуального барьера.
